# 10 — Squash the Postgres app and management chains into a first-deploy baseline

Squash both Postgres linear-migration chains so each is `0000_init_helpers.sql` +
`0001_*_schema.sql`, point the readiness markers at the two `0001` files, and regenerate the
`0004`/`0005` init baselines. The final schema does not change; this plan proves that with a
before/after diff of the generated baselines.

This plan also holds the operator wipe commands the set's last prompt carries
(§ Operator wipe for the last prompt). Nothing in this plan connects to a cluster or drops a
database that is not a throwaway Docker container the scripts create.

- Edited by hand: `infra/k8s/base/ops/kustomization.yaml`, the two `.env` files, and one comment
  each in `squash-linear-migrations.sh` and `run-linear-migrations.sh` (step 9, after every run).

## What stays true

- The squash goes through `scripts/database/squash-linear-migrations.sh --write`. Never write or
  concatenate `0001_*` by hand (`.cursor/rules/linear-baseline-0004.mdc`).
- The final schema, grants, default privileges, seeded reference rows, functions, and the
  `listener_identity` schema are byte-identical before and after (proved in step 7). If they are
  not, stop and report BLOCKED with the diff; do not "fix" SQL.
- `0000_init_helpers.sql` in each chain is not edited.
- The `0004`/`0005` gz archives are only written by `scripts/database/generate-linear-baseline.sh`.
- No `git add`, `git rm`, or commit. Delete files with `rm`; the operator stages.
- The four `add_by_rss_*` SQL functions from the old `0020` file stay in the schema (they move
  into `0001_app_schema.sql`). `apps/api/src/test/add-by-rss-feed-identity.integration.test.ts`
  calls them, and the fixed facts keep the final schema unchanged.
- Plain `--` comments in the old migration files do not survive the squash (`pg_dump` keeps only
  `COMMENT ON`). That is expected. The listener-id separation constraint those comments described
  lives in `.cursor/rules/popularity-listener-id-separation.mdc`.

## Steps

1. Load the Nix env once (`eval "$(direnv export zsh)" && node --version`; the scripts need bash
   5 for `mapfile`, plus `python3`, `gzip`, and `shasum`/`sha256sum`). Confirm Docker is up
   with `docker info`. If Docker is not running or a tool is missing, stop and report BLOCKED —
   the squash needs a person to start Docker.

2. Capture the pre-squash baselines from the current chain (not from the committed gz, which may
   lag):

   ```bash
   mkdir -p .artifacts/first-deploy-squash/before .artifacts/first-deploy-squash/after
   bash scripts/database/generate-linear-baseline.sh .artifacts/first-deploy-squash/before
   gzip -dc .artifacts/first-deploy-squash/before/0004_app_linear_baseline.sql.gz > .artifacts/first-deploy-squash/before-app.sql
   gzip -dc .artifacts/first-deploy-squash/before/0005_management_linear_baseline.sql.gz > .artifacts/first-deploy-squash/before-management.sql
   ```

3. Run the squash: `bash scripts/database/squash-linear-migrations.sh --write`. It rewrites both
   `0001_*_schema.sql` files from the full chain.

4. Delete every app file `0002_*.sql` through `0031_*.sql` and every management file
   `0002_*.sql` through `0004_*.sql` listed in § Files, with `rm`. Each directory must then hold
   exactly `0000_init_helpers.sql` and its `0001_*_schema.sql`.

5. Edit `infra/k8s/base/ops/kustomization.yaml`:
   - In `podverse-ops-migration-scripts` literals:
     `API_EXPECTED_MIGRATION_FILENAME=0001_app_schema.sql` and
     `MANAGEMENT_API_EXPECTED_MIGRATION_FILENAME=0001_management_schema.sql`.
   - `podverse-ops-app-linear-migrations` `files` lists only `app/0000_init_helpers.sql` and
     `app/0001_app_schema.sql`. Keep its ServerSideApply annotation and comment (the squashed
     `0001_app_schema.sql` is still above 256KiB).
   - `podverse-ops-management-linear-migrations` `files` lists only
     `management/0000_init_helpers.sql` and `management/0001_management_schema.sql`.
   - Leave `MIGRATION_BUNDLE_SHA=linear-migrations-v1` as it is (hash-suffixed ConfigMap names
     already force fresh job pods).

   Then set `API_EXPECTED_MIGRATION_FILENAME=0001_app_schema.sql` in
   `infra/k8s/base/api/source/api.env` and
   `MANAGEMENT_API_EXPECTED_MIGRATION_FILENAME=0001_management_schema.sql` in
   `infra/k8s/base/management-api/source/management-api.env` (unquoted, per
   **env-file-formatting**). The two `deployment.yaml` init containers already read the env vars;
   do not edit them.

6. Fixed-point check. Re-run the squash without `--write` against the two-file chains and compare:

   ```bash
   bash scripts/database/squash-linear-migrations.sh
   cmp .artifacts/squash-linear-migrations/0001_app_schema.sql infra/k8s/base/ops/source/database/linear-migrations/app/0001_app_schema.sql
   cmp .artifacts/squash-linear-migrations/0001_management_schema.sql infra/k8s/base/ops/source/database/linear-migrations/management/0001_management_schema.sql
   ```

   Both must match. A difference means the squashed file does not reproduce itself; read the diff.
   Report it and stop BLOCKED unless it is limited to statement order with identical objects, in
   which case say so in the final message.

7. Regenerate and verify the init baselines, then prove the schema did not change:

   ```bash
   bash scripts/database/generate-linear-baseline.sh
   bash scripts/database/verify-linear-baseline.sh
   gzip -dc infra/k8s/base/db/source/bootstrap/0004_app_linear_baseline.sql.gz > .artifacts/first-deploy-squash/after-app.sql
   gzip -dc infra/k8s/base/db/source/bootstrap/0005_management_linear_baseline.sql.gz > .artifacts/first-deploy-squash/after-management.sql
   diff .artifacts/first-deploy-squash/before-app.sql .artifacts/first-deploy-squash/after-app.sql
   diff .artifacts/first-deploy-squash/before-management.sql .artifacts/first-deploy-squash/after-management.sql
   ```

   The only allowed differences are the `linear_migration_history` seed rows at the end of each
   file (two rows per chain after the squash, with the new `0001` checksum) and the
   `setval('public.linear_migration_history_id_seq', …)` line. Any other difference is a schema
   change: stop and report BLOCKED with the diff.

8. Static checks: `bash scripts/database/validate-linear-migrations.sh` (filenames, order, and the
   ops kustomization file lists). Then confirm nothing outside `release-notes/` and `.llm/` still
   names a deleted file or an old marker:

   ```bash
   rg -n "0031_account_api_key|0004_admin_session" --glob '!release-notes/**' --glob '!.llm/**'
   ```

   Hits in files other areas own are expected until their prompts run; list them in the final
   message. A hit in a file this plan owns is a miss to fix.

9. After every script run above has finished, make the two comment edits:
   - `scripts/database/squash-linear-migrations.sh` header: replace "One-time (or repeat) squash
     helper: materialize 0001_*_schema.sql from the current multi-file linear chain without
     concatenating evolutionary migrations." with "Squash helper: materialize 0001_*_schema.sql
     from the current multi-file linear chain without concatenating evolutionary migrations. A
     squash changes 0001's checksum, so every database built from the previous chain must be
     dropped and recreated." Do not change any line the script writes into its output.
   - `infra/k8s/base/ops/source/database/runner/run-linear-migrations.sh`, the comment above
     `pg_advisory_xact_lock`: replace "Same connection/transaction as migration SQL; session lock +
     unlock across separate psql -c was invalid and caused ExclusiveLock warnings." with "The lock
     is transaction-scoped and shares the migration's connection, so it covers the whole file and
     the history insert."

10. Append the release-notes entry (§ Release scratchpad), or put it in the final message when this
   prompt shares a phase with other prompts (**release-notes-scratchpad**).

### Alpha cluster

Order matters. The wipe must happen after the GitOps pin points at the release that carries this
set, so Postgres init loads the new `0004`/`0005` baselines. Wiping first would reload the old
baselines and the migrate jobs would stop on a `0001` checksum mismatch.

1. **`k.podcastdj.com` repo root**, before committing the pin. Both markers must be unset in the
   overlay or set to the `0001` filenames. If this prints an old filename, change it in the same
   commit as the pin.

```bash
git grep -n 'EXPECTED_MIGRATION_FILENAME' -- apps/podverse-alpha
```

2. Pin, push, and wait for `podverse-alpha-db` and `podverse-alpha-ops` to sync, per
   `abcdeploysteps podverse alpha`. Confirm the kube context:

```bash

kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}'
```

3. **`k.podcastdj.com` repo root.** Reset the database volume. The script asks `y/N`; keep it alone
   in its paste. It pauses Argo auto-sync for `podverse-alpha-db`, scales Postgres to 0, deletes
   PVC `db-data-podverse-db-0` (app and management databases share it), and restores auto-sync so
   Argo recreates Postgres and its volume.

```bash
bash ./apps/podverse-alpha/scripts/ops/reset-alpha-db.sh
```

4. Wait until init has loaded both baselines (two history rows in the management database, which
   loads last), then until the StatefulSet is ready after init restarts Postgres:

