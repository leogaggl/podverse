# First-deploy squash — summary

Models and run order live in `COPY-PASTA.md` once Close writes it. This file holds the requirement
ledger, the areas, and which area owns which files.

Squash every migration chain in this monorepo (v5) into a first-deploy baseline, then sweep docs,
code, and comments for material whose only job is upgrading an older state of this monorepo.

## Fixed facts every area plans against

Areas plan at the same time, so these outcomes are settled here and do not wait on area A or B:

- After the squash, each Postgres chain is exactly two files: app `0000_init_helpers.sql` +
  `0001_app_schema.sql`, management `0000_init_helpers.sql` + `0001_management_schema.sql`. Every
  `0002_*.sql` and later file is deleted. `0001_*` is regenerated by
  `scripts/database/squash-linear-migrations.sh --write`, not written by hand.
- Readiness markers become `API_EXPECTED_MIGRATION_FILENAME=0001_app_schema.sql` and
  `MANAGEMENT_API_EXPECTED_MIGRATION_FILENAME=0001_management_schema.sql`.
- The final Postgres schema is unchanged by the squash itself. A sweep that finds a column, table,
  or index that exists only for an older v5 state does not edit SQL; it records the finding under
  `## Decisions` in its final message, naming the object and the code that would change.
- The mobile SQLite chain in `apps/mobile/src/data/db/migrations.ts` becomes one first migration
  that produces today's final schema. Later mobile migrations append after it.
- A reference to an old migration file (`0016_description_length_tiers.sql`, user_version 14, and
  so on) becomes false after the squash. Rewrite it to name the table, column, or `0001_*` file,
  or drop it when the reference adds nothing.

## Constraints for every area

- v5 is this monorepo. v4 / podverse-rn is out of scope: do not remove v4 compatibility (deep
  links, imports such as `importLegacyMembershipExpiry`, legacy-app references in docs).
- Keep current product behavior, including features carried over from the previous app.
- A removal must exist only to upgrade an older state of this monorepo: an older schema, older
  stored rows or device data, an older v5 deployment, or a plan that will not exist for a first
  deploy.
- "Legacy" in this repo often means v4, a deprecated platform API (`expo-file-system/legacy`), or
  a third-party term. Read each hit before classifying it.
- Comments follow `.cursor/rules/comments-future-forward.mdc`: rewrite or drop a comment that only
  describes an older schema, deployment, or plan; keep one that states a constraint of the code.
- No agent connects to a cluster or drops data. Wipe commands go to the operator.
- Do not edit `release-notes/scratchpad.md` entries written by other changes, `.llm/plans/**`
  (including `completed/` and `cross-device-playback/`), or generated `.gz` baselines by hand.
- An area edits only files it owns (§ File ownership). A finding in another area's file goes in
  `## Notes for later prompts` naming the file and the owning area.
