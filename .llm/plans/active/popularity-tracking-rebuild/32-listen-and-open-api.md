## Request contract

### `POST /stats/listen`

Body (JSON), validated with Joi:

| Field | Rule | Meaning |
| --- | --- | --- |
| `item_id_text` | string; exactly one of this and `clip_id_text` | the episode or track heard (a soundbite listen sends its item) |
| `clip_id_text` | string; exactly one of this and `item_id_text` | the clip heard; the server derives its item and channel |
| `client_listen_id` | `Joi.string().uuid()`, required | one random id per listening session, generated by the device; every report for that session reuses it |
| `seconds_heard` | integer, 0–86400, required | media seconds actually played in this session so far (not wall-clock, not seek distance) |
| `completed` | boolean, default `false` | the session reached the end of the item or clip |

The body carries no device time. The server's receive time is the only clock: it decides the
daily-totals day and the time taste scores fade from, so a report sent after offline time counts
on the day it arrives. `DEFAULT_JOI_VALIDATION_OPTIONS` strips unknown keys
(`stripUnknown: true`), so the controller passes only the fields above.

Clients send the first report only once `isCountedListen` from `@podverse/helpers`
(`@podverse/helpers/popularityListen` on mobile) is true for the item's or clip's duration. They
may send later reports for the same session (more seconds, or `completed: true`); the server keeps
the larger seconds and a sticky `completed`, and never counts the session twice. Add by RSS items
are never sent; they have no server row.

Responses (body `{ result }`, where `result` is plan 30's `PopularityListenResult`):

| Status | When | Body |
| --- | --- | --- |
| 201 | `counted` — a new session was stored | `{ result: 'counted' }` |
| 200 | `updated`, `unchanged`, or `daily_cap_reached` | `{ result }` |
| 400 | Joi failure, or `below_threshold` | Joi's usual body; for the threshold `{ message: 'Listen does not meet the counted-listen rule.', code: 'listen_below_threshold' }` |
| 401 | no session | as today |
| 403 | terms, membership expired, no `trackStats` capability (from `ensureAuthenticated`), or consent not current (`assertListenStatsAllowed`, or the service's `not_allowed`) | consent case: `{ message: 'Listen stats tracking is disabled for this account', code: 'popularity_tracking_not_allowed' }` |
| 404 | `not_found` | `{ message: 'Not found', code: 'not_found' }` |
| 410 | `clip_source_removed` | `{ message: CLIP_SOURCE_REMOVED_MESSAGE, removed: true }` (as today) |
| 429 | per-account rate limit | the shared limiter body (`buildRateLimit429Body`) and `RateLimit-*` headers |

Client handling (for area H): 2xx is done. 400, 403, 404, and 410 are final; drop the report.
429 and 5xx are retryable later with the same `client_listen_id`; a mobile outbox keeps the row.

### `POST /stats/open`

Body: exactly one of `account_id_text` (a profile opened) or `playlist_id_text` (a playlist
opened), both strings.

| Status | When | Body |
| --- | --- | --- |
| 201 | `counted` — the first open of that profile or playlist by this listener today | `{ result: 'counted' }` |
| 200 | `unchanged` (already opened today) or `own_content` (own profile or own playlist) | `{ result }` |
| 400, 401, 403, 404, 429 | as for listen | same bodies |

Opens never feed the Taste Profile (R43). Only web sends them; mobile does not (R44, area H).

## Settings (R45, R46, R47)

| Env | Default | Meaning |
| --- | --- | --- |
| `STATS_TRACK_MAX_PER_MINUTE` | `60` | per-account requests per minute across `/stats/listen` and `/stats/open` |
| `STATS_LISTEN_DAILY_CAP` | `300` | stored listens per listener per UTC day; reports for an already-stored session do not count against it |

Defaults: a counted listen needs at least 15 seconds of audio even for the shortest item, and most
need 45–60, so live playback sends a few reports a minute; 60 leaves room for completion reports
and opens. 300 covers a full day of three-minute music tracks with headroom, while bounding how
many entities one paid account can touch per day; the first-of-day rule already limits each
entity to one count per listener per day.

## Popularity Tracking counts real listens, with a rate limit and daily cap

- Surfaces: api, k8s base env, web and mobile clients (once they send the new reports)
- Change: `POST /stats/listen` and `POST /stats/open` replace the five `POST /stats/{account,channel,clip,item,playlist}` routes, which are removed. A listen is reported once per listening session, after 60 seconds or 25% of the item (whichever comes first), with seconds heard and whether it finished; later reports for the same session update it. The request carries no device time: the server's receive time dates the listen for daily totals and Taste Profile score decay, so a report sent after offline time counts on the day it arrives. Each listen stores one event, adds to anonymous daily totals (one count per listener per item, show, and clip per UTC day), and updates the listener's Taste Profile with recent and long-term scores, except for shows in Hidden From Taste Profile. Profile and playlist opens count once per opener per day, never for your own profile or playlist, and never feed the Taste Profile. Both routes keep the Premium, capability, and consent gates and add a per-account rate limit; listens also have a daily cap.
- Who notices: Premium listeners with Popularity Tracking on; popularity sorts once the jobs roll daily totals up
- Operator steps: optional `STATS_TRACK_MAX_PER_MINUTE` (default 60) and `STATS_LISTEN_DAILY_CAP` (default 300) on the API
